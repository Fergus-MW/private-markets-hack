The seam the demo depends on

The graph is done for the demo when the export for 30 June 2026 equals terms table v1 and for 30 September equals v2, row for row. In this ontology that export is one query over Term Fact filtered by validity, pivoted from long to wide. Nothing else on the page is on the critical path.

Modelling rules

Seven decisions to make once

Two clocks, never delete

Every term fact, rule and crosswalk row carries in-force dates and a known-since timestamp. Changes close the old fact and add a new one; nothing is deleted.

Received 6 July, effective 1 July answers both of the fund manager's questions: the Q2 run on 30 June was not wrong, and the Q3 run must change. Any store can hold two date columns; the discipline is the point.

Project is an instance, not a schema

A Q2-26 reconciliation is a node linked to a period, a scope, tasks, decisions, findings and a deliverable. Its contents are shared classes tagged with the project.

Project-specific classes kill the cross-period questions: did this gap recur, what did we decide last quarter, which accounts have had three exceptions running.

The crosswalk is a node

Each mapping row is a first-class record with a status and an approver, and every ledger line reaches the target chart through it.

In v4c the two gaps, the ambiguous fallback and the 389 trans-type-only mappings are the judgement. A lookup table hides them; a node lets a finding point at one.

Everything actionable cites a chunk

Term facts, findings, decisions and rules all point at chunks of documents, using the stable chunk IDs the ingestion service already produces.

That single edge turns the existing ingestion layer into the evidence base for the QC half without extraction or embeddings, and it is what the provenance panel walks.

The gate reads a snapshot, not the graph

A terms snapshot is a hashed export of the in-force facts for one entity on one date. Every gate run records which snapshot and which report it used.

Two hashes make every past statement re-derivable and let the graph fail on stage without the gate noticing.

Lines stay in tables

Keep transaction lines and allocations as SurrealDB records with plain fields. Put batches, aggregates per account, runs and findings in the graph.

Thirty-four thousand lines a quarter as graph nodes make the graph a slow copy of the GL. SurrealDB does both shapes, so use each where it is cheap.

Identifiers are system-scoped

An identifier record carries the system and the value. Objects are related to their identifiers rather than storing a bare number.

The registrar, Corvus and Helio each issued IDs for the same investor account; the loader is the act of translating between them.

SurrealDB shape

How it lands in the database

A sketch of the node tables, the fact table with two clocks, the edges as relation tables, and the three operations the demo performs. Syntax follows SurrealDB 2.x; check the exact keywords against the version deployed on the VM before relying on them.

-- Nodes: plain tables, one per class
DEFINE TABLE legal_entity SCHEMAFULL;
DEFINE FIELD name     ON legal_entity TYPE string;
DEFINE FIELD currency ON legal_entity TYPE string;

DEFINE TABLE investor_account SCHEMAFULL;
DEFINE FIELD name ON investor_account TYPE string;

-- Identifiers: system-scoped, unique per system
DEFINE TABLE identifier SCHEMAFULL;
DEFINE FIELD system ON identifier TYPE string;  -- corvus | helio | rfx
DEFINE FIELD value  ON identifier TYPE string;
DEFINE INDEX uniq_identifier ON identifier FIELDS system, value UNIQUE;

-- Term facts: two clocks, never deleted
DEFINE TABLE term_fact SCHEMAFULL;
DEFINE FIELD subject     ON term_fact TYPE record<investor_account|legal_entity>;
DEFINE FIELD predicate   ON term_fact TYPE string;   -- mgmt_fee_rate_pa, fee_basis …
DEFINE FIELD object      ON term_fact TYPE any;
DEFINE FIELD valid_from  ON term_fact TYPE datetime;           -- in force from
DEFINE FIELD valid_to    ON term_fact TYPE option<datetime>;   -- closed, not deleted
DEFINE FIELD recorded_at ON term_fact TYPE datetime;           -- known since
DEFINE FIELD version     ON term_fact TYPE string;
DEFINE INDEX fact_lookup ON term_fact FIELDS subject, predicate, valid_from;

-- Documents: the existing table, plus kind and email fields
DEFINE FIELD kind        ON document TYPE option<string>;  -- side_letter | lpa | email | statement
DEFINE FIELD received_at ON document TYPE option<datetime>;
DEFINE FIELD sender      ON document TYPE option<record<person>>;

-- The gate's audit trail
DEFINE TABLE gate_run SCHEMAFULL;
DEFINE FIELD as_of                ON gate_run TYPE datetime;
DEFINE FIELD entity               ON gate_run TYPE record<legal_entity>;
DEFINE FIELD schedule_sha256       ON gate_run TYPE string;
DEFINE FIELD terms_snapshot_sha256 ON gate_run TYPE option<string>;
DEFINE FIELD mode                 ON gate_run TYPE string;   -- terms | arithmetic-only
DEFINE TABLE check_result SCHEMAFULL;
DEFINE FIELD run    ON check_result TYPE record<gate_run>;
DEFINE FIELD check  ON check_result TYPE string;   -- TC01 … TC10
DEFINE FIELD status ON check_result TYPE string ASSERT $value IN ['PASS','FAIL','SKIPPED'];
DEFINE FIELD tier   ON check_result TYPE string;
DEFINE FIELD amount ON check_result TYPE option<decimal>;
-- Edges: relation tables with typed ends
DEFINE TABLE in_entity     TYPE RELATION IN investor_account OUT legal_entity;
DEFINE TABLE identified_by TYPE RELATION
  IN legal_entity|investor_account|deal|position|gl_account OUT identifier;
DEFINE TABLE cites         TYPE RELATION IN term_fact|finding|decision|rule OUT chunk|document;
DEFINE TABLE closes        TYPE RELATION IN term_fact OUT term_fact;
DEFINE TABLE supersedes    TYPE RELATION IN document OUT document;
DEFINE TABLE received_via  TYPE RELATION IN document OUT document;  -- letter -> email
DEFINE TABLE governed_by   TYPE RELATION IN investor_account OUT document;
DEFINE TABLE maps_from     TYPE RELATION IN crosswalk OUT trans_type;
DEFINE TABLE maps_to       TYPE RELATION IN crosswalk OUT trans_type;
DEFINE TABLE allocated_for TYPE RELATION IN investor_allocation OUT investor_account;
DEFINE TABLE verifies      TYPE RELATION IN gate_run OUT report;
DEFINE TABLE raises        TYPE RELATION IN gate_run OUT finding;
DEFINE TABLE about         TYPE RELATION
  IN finding OUT investor_account|crosswalk|batch|report_line|legal_entity;

The test

Three questions the gate must answer in a few hops

The first two are asked on stage. If a class sits on none of these paths it is probably decoration. Query shapes are illustrative and untested against a live instance.

What was Trentcombe's fee rate on 15 May, and on 15 August?

-- run once with each date; expect 0.0085 then 0.0075
SELECT object, valid_from, recorded_at, ->cites->chunk AS clause
FROM term_fact
WHERE subject = investor_account:⟨7335_02891⟩
  AND predicate = 'mgmt_fee_rate_pa'
  AND valid_from <= $on
  AND (valid_to IS NONE OR valid_to >= $on);

One hop for the value, one more for the clause, two more through the document to the email. That walk is the provenance panel.

Export the terms snapshot the gate will check against

-- terms_as_of(2254, 2026-09-30): long form; pivot to the fixture columns on export
SELECT subject, predicate, object, id AS fact_id, recorded_at
FROM term_fact
WHERE subject->in_entity->legal_entity CONTAINS legal_entity:⟨2254⟩
  AND valid_from <= $as_of
  AND (valid_to IS NONE OR valid_to >= $as_of);
-- hash the pivoted rows; that hash goes on the gate_run

This is the seam. The contract test compares its output with terms table v1 or v2, cell for cell.

Which fee runs used Trentcombe's old offset?

SELECT id, as_of, terms_snapshot_sha256, ->verifies->report AS report
FROM gate_run
WHERE entity = legal_entity:⟨2254⟩
  AND as_of >= d'2026-07-01'
  AND terms_snapshot_sha256 != $v2_snapshot_hash;

Answerable only because every run records the snapshot hash it consumed. This is the question the audience asks after the demo.

Open for Fergus

Five things to decide together

  1. Both clocks or one. The store should hold valid dates and recorded_at on every fact. If it can only hold one, keep valid dates on the fact and put recorded_at on the document node, and agree that before the fixture is loaded.
  2. The maker-checker step. When a model extracts the delta from the email, the extracted facts should sit without a valid_from until a Decision node approves them, and the approval itself is a fact with a person on it. For the demo the pre-built delta is the fallback.
  3. Run records in the graph or as files. The gate already writes its runs in triple shape. Loading them makes the third question above a live query; leaving them as files is fine for the demo.
  4. Where the lines live. Ledger lines and allocations as SurrealDB records alongside the graph, or does the graph hold aggregates and point back at the loader file by batch, journal entry, transaction and investor?
  5. Investor identity. Organisation carries the Corvus common ID, Investor Account the specific ID and the registrar ref. Agree the merge key when names differ between systems, which happens in about one row in a hundred of the investor mapping.
